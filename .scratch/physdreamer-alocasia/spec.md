## Problem Statement

仓库现在能模拟的 3DGS 只有**单个物体**的扫描：`bread`、`wolf`、`football` 都是一件东西，
整个被切成点阵、整个会动、整个可以抓。PhysDreamer 的四份数据（alocasia / carnations /
hat / telephone）是**场景级**的扫描——一盆植物连同它所在的整间屋子——而且它们想表达的运动
不是"整件东西动"，是"这件东西的一部分动，另一部分钉在原地，其余的屋子根本不参与"。

按仓库现在的能力直接加载这份数据，会得到三种失败，都不是 bug 而是能力缺口：

1. **整间屋子被当成一个物体**。`point_cloud.ply` 是 787777 个高斯，包含墙、桌子、背景玩具
   盒。`voxelizeCloud` 会给它们全部发明一个内部、切成点阵——几何上荒谬，算力上不可能。
2. **一施加力就整株飞走**。没有任何机制把花盆钉在空间里。仓库现有的 `KinematicDrive` 是
   "被抓住的那一刻确定、松手就还回去"的临时集合，不是永久锚定。
3. **零重力是场景的属性，而仓库把它当全局常量**。`Simulator.DEFAULT_PARAMS.gravity` 写死
   `[0,-9.81,0]`，场景碰不到。PhysDreamer 的四份场景全部跑在 `g = [0,0,0]`（官方
   `demo.py:332`），不是偷懒——一株没有根系约束的植物在重力下会直接塌掉。

另外还有两个更安静的问题：这份数据的世界帧是 COLMAP 的（z-up），**尺度不是米**，而仓库从
CFL 到抓取半径到水缸边界全部是米制；而且同一份扫描分散在三个文件里，它们必须共用**一个**
变换，而 `loadCapture` 的固定顺序是每份点云各自量各自的包围盒、各自算各自的缩放。

## Solution

把 PhysDreamer 的三层语义搬进仓库已有的 `body` / `scenery` 之分，并且**整套东西收束在应用
层**——physdreamer 只是这台引擎的一个用户，不是它的一等公民。

对使用者来说，结果是：打开 `?scene=alocasia`，看到那盆 alocasia 站在原地；用左键拖住一片
叶子，叶子跟着走并且带着叶柄弯曲；花盆纹丝不动，也抓不住；松手之后叶子回弹、摆荡、停下；
没有任何东西往下掉。

做法分三段：

- **离线一次**：一个 `physdreamer_tools/` 下的 node 脚本，把三个原始文件读进来，核对 up 轴、
  转成 y-up、按声明的高度缩放到米制、把 `point_cloud` 按到 `clean_object_points` 的距离切成
  "物体"和"背景"，产出到 `public/splats/alocasia/` 下。产物不进 git。
- **运行时一次**：一个 `scene/` 下的 alocasia 场景，加载物体点云和可动点云，直接组装
  `SoftBody`（不走 `body/factory.js`），在离散化之后算出锚定节点集合。
- **核心只碰一处**：锚定结论怎么写进点阵。这一处**不在本 spec 内**，见
  `issues/01-anchor-mechanism.md`。

## User Stories

1. 作为引擎开发者，我想用 `?scene=alocasia` 打开一个 PhysDreamer 场景，这样我不用改代码就能
   在四个场景之间切换。
2. 作为引擎开发者，我想让这个场景的全部 physdreamer 专有知识只出现在 `scene/` 的一个文件和
   `physdreamer_tools/` 里，这样 `assets/`、`body/`、`sim/`、`render/` 不需要知道
   PhysDreamer 存在。
3. 作为引擎开发者，我想把三个原始 PLY 的切分放在离线脚本里，这样 `assets/splats/` 那扇门不必
   学会"三文件语义"这种只有一个用户的概念。
4. 作为引擎开发者，我想让脚本产出的点云已经是最终世界坐标，这样运行时不需要再摆一次，物体和
   将来的背景共用一个帧就变成构造性的事实而不是需要维护的约定。
5. 作为引擎开发者，我想让脚本在产出时打印它推断和应用的每一个量（up 轴夹角、缩放系数、物体
   尺寸、由此推出的整间屋子尺寸），这样"高度 0.30 m"这个声明可以被核对而不是被相信。
6. 作为引擎开发者，我想让脚本在 up 轴偏离 +Z 超过阈值时直接报错停下，这样一份帧不对齐的新数据
   不会悄悄产出一个歪的场景。
7. 作为引擎开发者，我想让派生资产进 `.gitignore`，这样仓库里不会同时存在"脚本"和"脚本某一次
   的运行结果"两份真相。
8. 作为引擎开发者，我想让脚本可重跑且输出确定，这样换台机器只要跑一遍就能复现同一个场景。
9. 作为引擎开发者，我想让物体点云只包含前景高斯，这样点阵包住的是那盆植物而不是整间屋子。
10. 作为引擎开发者，我想让背景高斯被切进单独一份产物，这样以后接背景时不需要重新设计资产契约。
11. 作为观看者，我想看到花盆和盆土在整个过程中完全不动，这样这株植物看起来是长在盆里的而不是
    悬浮着的。
12. 作为操作者，我想用左键拖住一片叶子让它跟着走，这样我能用仓库已有的交互方式驱动这个场景。
13. 作为操作者，我想在试图抓花盆时抓不住（射线直接穿过去找下一个能抓的东西），这样"哪些部分
    是活的"这件事通过手感就能知道，不需要看调试视图。
14. 作为操作者，我想在松手之后看到叶子回弹并逐渐停下，这样这个场景是有弹性的而不是被拖到哪算
    哪。
15. 作为操作者，我想让整个场景里没有任何东西往下掉或者塌陷，这样我不需要先等它稳定下来才能
    开始交互。
16. 作为操作者，我想在这个场景里仍然能用面板改刚度、密度、阻尼，这样我能自己找到"看起来像
    植物"的那组参数。
17. 作为操作者，我想在这个场景里仍然能用面板的抓取半径滑杆，这样我能在"抓一把"和"抓整片叶子"
    之间自己调。
18. 作为操作者，我想在这个场景里仍然能打开点阵调试视图，这样叶片被印成一格厚的板这件事我能
    亲眼看见而不是只在文档里读到。
19. 作为引擎开发者，我想在控制台看到锚定节点占总节点的比例，这样"锚定集合是不是空的/是不是把
    整株都钉住了"在第一帧就能判断。
20. 作为引擎开发者，我想在控制台看到 `lattice.volume` 相对包围盒体积的占比，这样"叶片被封口
    桥接成一坨"这个已知风险有一个可读的数而不是靠肉眼。
21. 作为引擎开发者，我想让这个场景在 60 fps 下不丢时（`droppedTime == 0`、每帧步数 ≤ 24），
    这样我不需要为一个应用层场景去顶开核心的时序预算。
22. 作为引擎开发者，我想让锚定判据是一个不认识 GPU、不认识点阵实现的纯函数，这样它能在单元
    测试里用合成数据验证，不需要 187 MB 的真实数据也不需要显卡。
23. 作为引擎开发者，我想让锚定区域在点阵变细时收敛到同一块世界空间区域，这样"钉住多少材料"
    不随分辨率变化——和 `sim/grip.js` 对抓取要求的是同一条性质。
24. 作为引擎开发者，我想让 up 轴核对和米制摆放也是纯函数，这样它们能被单测钉住，而不是只能
    靠"渲染出来看着像"来验证。
25. 作为引擎开发者，我想让 `architecture.test.js` 和 `docs.test.js` 在不修改的情况下继续通过，
    这样这次接入没有偷偷破坏分层。
26. 作为将来接入 carnations / hat / telephone 的人，我想让第二个场景只需要一份声明（文件路径、
    高度、分辨率、材料）而不需要新逻辑，这样"四个场景"这件事不是四份代码。
27. 作为将来接入背景的人，我想让背景走 `scene.scenery` 这条已经存在的路，这样接入是加一行而
    不是改设计。
28. 作为读 `DECISIONS.md` 的人，我想知道为什么切分在离线、为什么这个场景不用 `body/factory.js`、
    为什么尺度按高度而不是仓库惯例的最长轴，这样三个看起来像不一致的地方都有出处。

## Implementation Decisions

### 数据语义（已对着官方仓库核实）

- `moving ⊂ clean ⊂ point_cloud`。`clean_object_points.ply` 是整个前景物体，
  `moving_part_points.ply` 是其中允许运动的子集，两者都是纯 xyz 点云（`property float x/y/z`）。
  **没有任何文件显式记录固定点**：固定集是 `clean − moving` 算出来的。
- 官方用"离 `clean_object_points` 超过 0.01（COLMAP 单位）的高斯不参与模拟"把
  `point_cloud` 切成前景/背景；用"离 `moving_part_points` 超过半个网格的粒子被冻结"定出固定集。
- 官方重力是 `[0,0,0]`，阻尼实际上没开（`grid_v_damping_scale = 1.1 > 1.0`，那个 kernel 不进），
  激励是学出来的初速度场或一次冲量，**没有风场也没有持续力**。
- 四份数据的 COLMAP 世界帧**本来就重力对齐**：相机 up 的均值与 +Z 的夹角分别是 0.3° / 0.2° /
  0.2° / 0.0°。所以 `place.js` 现成的 `z-up` 约定原样够用，**不需要写 up 估计器**。
  （相机中心最小二乘平面那条路已验证不可用：法向偏 28.8°，奇异值 1 / 0.727 / 0.327，
  手持绕拍的相机中心根本不共面。）

### 三层划分

- **body**（进点阵、被解算、被绘制）= `point_cloud` 中离 `clean_object_points` 足够近的那些
  高斯。渲染几何与解算几何是同一份，和 `bread` 完全同构。
- **scenery**（只绘制、不步进）= 剩下的全部高斯。**本 spec 不接**，见 Out of Scope。
- **锚定判据的原料** = 变换后的 `moving_part_points`。发可动点而不是发固定点差集：判据写成
  "节点周围 h 内**没有**可动点则锚定"，一个文件就够，且和官方判据同形。

### 离线工具

- 新目录 `physdreamer_tools/`，在 `src/` 之外。`architecture.test.js` 和 `docs.test.js` 都只扫
  `src/`，所以 `ARCHITECTURE.md §二` 的表和依赖表都不触发修改。
- 输入：一个场景目录（三个 PLY + `transforms_train.json`）加一个声明的高度。
- 三步，顺序固定：**核对 up → 转正并缩放 → 切分**。
  - 核对：读 `transforms_train.json` 每帧 c2w 的第 1 列（相机 up），取均值，与 +Z 夹角超过阈值
    就抛错。通过之后应用 `place.js` 的 `z-up` 四元数。
  - 缩放摆放：按**转正后的 y 向高度**缩放到声明值，底部落在 y = 0，x/z 居中。三个文件共用这一个
    变换。
  - 切分：在 `clean_object_points` 上铺一张均匀网格，逐高斯查最近距离，阈值以内归物体、以外
    归背景。
- 输出：物体高斯（3DGS PLY，仓库现有 `assets/splats/ply.js` 能读）、可动点（纯 xyz PLY）、
  背景高斯（产出但本轮不加载）。落在 `public/splats/alocasia/`，加进 `.gitignore`。
- 报告（stdout）：相机 up 与 +Z 的夹角、缩放系数、物体转正后的三向尺寸、由同一变换推出的
  **整间屋子尺寸**、物体/背景的高斯数。屋子尺寸是这份声明唯一可核对的地方。
- 复用方向合法且刻意：工具从 `src/` import 读 PLY 与旋转四元数，反向不发生。

### 运行时场景

- 新的 `scene/` 场景，注册进 `SCENES`，键名 `alocasia`（不是 `physdreamer`——另外三个会来）。
- **不走 `body/factory.js` 的 `splatBody`**。`loadCapture` 的顺序里含"各自量各自的包围盒、
  各自算缩放"，这和"三个文件共用一个变换"直接冲突。场景自己 `loadCloud` + `cleanCloud` 之后
  直接构造 `SoftBody`（`source` 与 `render` 指向同一份 cloud）。`factory.js` 本来只是便利函数，
  绕开它是零核心改动。代价：`capture.js` 那份可核对报告这条路上没有，改由离线脚本打印。
- **锚定判据落在场景这一侧**，是一个纯函数：给节点静止位置、可动点、半径，返回要锚定的节点
  索引。规模是"节点数 × 178931"，暴力不可行，所以在可动点上铺一张边长等于半径的均匀网格，
  每个节点查 27 个桶。判据半径取**一个格子 h**，写成 h 的倍数而不是抄官方的归一化常数——
  那是对我们自己的离散化诚实。
- 依赖表检查过：`scene: ['body', 'assets', 'sim']` 已经允许 `scene/` 反查 `sim/discretize/`，
  所以那张网格可以复用 `voxelize.js` 现成的工具，**依赖表不改**。
- **重力**：`Scene` 增加一个可选字段，`main.js` 读进 `sim.params.gravity`。alocasia 声明
  `[0, 0, 0]`。不做 UI 开关——一个滑杆会把"这个场景为什么不塌"变成运行时状态，下次打开就
  不知道该是多少。
- **`decorate` 什么都不画**（不 import `glass.js`）：真实房间里立一个玻璃缸很荒唐。
- **`bounds`** 取物体包围盒各向外扩一点，地板落在 y = 0。零重力下六个解析平面基本不参与，
  但它仍然是相机取景的依据。

### 分辨率与材料（实时预算算出来的）

硬约束：`dt = min(1/240, 0.75 / (c/h))`，每帧最多 24 步，所以 60 fps 下不丢时要求
**c/h ≤ 1080 s⁻¹**。物体转正后最长轴约 0.38 m：

| 分辨率 | h | 允许波速 | 允许 E（ρ=1000, ν=0.4） |
|---|---|---|---|
| 16 | 23.8 mm | 25.7 m/s | 3.1e5 |
| **24** | **15.9 mm** | **17.2 m/s** | **1.38e5** |
| 32 | 11.9 mm | 12.9 m/s | 7.7e4 |
| 48 | 7.9 mm | 8.6 m/s | 3.4e4 |

- **取 R = 24**，材料从 `DEFAULT_MATERIAL` 起步（E ≈ 1.2e5, ρ = 1000, ν = 0.40）。R=24 那一行
  的上限 1.38e5 和默认值几乎重合。
- 对照官方：他们 grid 64 铺在单位立方体、物体占约 0.34，**等效分辨率约 22**，h 折合约 16 mm，
  和 R=24 同量级。他们 E=1e6 / ρ=2000 折合 c/h ≈ 1530，超预算 1.4 倍；折到我们预算内约
  E ≈ 2.8e5，**只软 3.5 倍，不是数量级**。
- 而"叶片被印成一格厚的板、弯曲刚度 ∝ 厚度³"这条**独立地**要求更软。两条论证同向，中间有余量。
- **不动 `MAX_STEPS_PER_FRAME`**：用一个应用层场景去顶开核心的时序预算，正是这次要避免的泄露。

### 不做的核心改动（每条都有理由）

- **不透传 `fill` / `seal`**。`voxelizeCloud` 收这两个参数但 `discretizeBody` 只往下传
  `resolution`。默认 `SEAL = 2` 在 h = 15.9 mm 下会桥接 32 mm 以内的缝，alocasia 的叶柄交汇处
  有糊成一坨的风险。**先用默认值跑，看到真的糊了再回来**——那时才知道该开的是 `seal` 还是
  `fill`。可读的判据见 Testing Decisions。
- **不动 `sim/grip.js` 的默认半径**。`setGripRadius` 已公开、面板滑杆已存在，场景需要什么自己
  调。但要记录一个已知后果：`DEFAULT_GRAB_RADIUS = 0.03 m` 的上界论证写的是"最小物体尺度约
  0.15 m"，对一株 0.30 m 的植物来说 0.03 m 的球大致是**整片叶子**；而且欧氏球不是测地邻域，
  抓在薄叶上会连带隔着空气的另一片。
- **不改依赖表**，因此不触发 CLAUDE.md 那条"改依赖表把理由追加进 DECISIONS.md"。

### 文档产出

- `DECISIONS.md` 追加**三条**（带日期、过去时、只追加）：
  1. 为什么切分在离线 `physdreamer_tools/` 而不是运行时（连同"考虑过没做的：运行时切分"及其
     理由）。同时把 `ARCHITECTURE.md` 欠账表那一行的修改理由并进这一条。
  2. 为什么这个场景绕开 `loadCapture` / `splatBody` 自己组装 `SoftBody`。
  3. 为什么尺度按转正后高度而不是仓库惯例的最长轴——它直接抵触 `place.js` 文档注释写着的惯例，
     不写下来就是一个看起来像 bug 的不一致。
- **不单独记**：不接背景、不透传 `fill`/`seal`、不动 `MAX_STEPS_PER_FRAME`、R=24、E 取默认值。
  这些是可逆的参数选择或"这一轮先不做"，写进上面条目的"考虑过没做的"里就够，单独成条会把
  `DECISIONS.md` 稀释成进度日志。
- `ARCHITECTURE.md` **只改一行**：欠账表第一行的到期条件。现在写的是"加第三份扫描时"，而我们
  正在加第四到第七份并且没还这笔债。改成更准的说法——声明仍由人写，但**带相机位姿的扫描可以
  核对声明**，真正到期的条件是出现一份没有位姿、声明无从核对的扫描。其余一字不动：`tools` 在
  `src/` 外，`src/` 里只多一个 `scene/` 下的文件，§二那张表是按目录列的，目录一个没变；§四的
  根一个没换，所以也不该多一个 4.x。
- **不写 `STATUS.md`**。CLAUDE.md 已经删掉了「接受新需求时把计划按里程碑写入 STATUS.md」那条
  规则和文档表里的那一行。

## Testing Decisions

好的测试只验证外部行为：给定输入数据，输出是什么。不验证"用了哪张网格""循环了几次"。仓库现有
的 `grip.test.js` / `pick.test.js` 是这条标准的样板——它们喂合成的 `Float32Array`，不碰 GPU、
不碰真实资产，断言的是集合和几何性质。

### 缝一：锚定判据（`src/` 里唯一的新逻辑）

一个纯函数，吃节点静止位置、可动点、半径，吐要锚定的节点索引。测试放 `test/unit/`，照
`grip.test.js` 写。断言：

- 半径内有可动点的节点**不**被锚定；一个都没有的**被**锚定。
- **分辨率无关性**：把节点间距减半、半径同步减半，锚定区域的边界在世界空间里移动不超过一个
  格子。这是 `grip.test.js` 对抓取要求的同一条性质（那里是"握住的材料量不随分辨率变化"），
  也是这条判据存在的理由——半径写成 h 的倍数，边界就该跟着 h 收敛而不是跟着 h 漂移。
- 输出确定且有序：同样输入两次调用给出同一个数组。
- 退化输入：可动点为空 → 全部锚定；可动点覆盖全部 → 一个都不锚定。两端都不抛错。

**先验样板**：`grip.test.js`（合成点阵 + 几何性质 + 分辨率对照）、`pick.test.js`（射线 miss
返回 -1 那类边界）。

### 缝二：离线变换（`physdreamer_tools/` 里的两个纯函数）

它不在 `src/`，但它值一条缝：出错的表现是画面"差不多但不对"，靠眼睛发现不了。

- **up 核对**：喂几组合成 c2w 矩阵。全部 +Z → 通过并返回接近 0 的夹角；整体倾斜超过阈值 →
  抛错；少数几帧歪掉（手持抖动）→ 均值仍然通过。
- **米制摆放**：喂一个已知包围盒和一个声明高度 → 断言缩放系数、底部落在 y = 0、x/z 居中。
  同一个变换作用在第二个包围盒（模拟背景）上 → 断言用的是**同一个**缩放系数而不是重新量的。

**不测**的：PLY 读写（`assets.test.js` / `splats.test.js` 已经覆盖 `ply.js`）、切分用的那张
网格（`voxelize.test.js` 覆盖同类工具）。

### 已有的、自动生效的

`architecture.test.js` 和 `docs.test.js` 不需要修改也不需要新增用例——它们扫 `src/`，新场景
落在已有的 `scene` 区域里，依赖表已经允许所需的边。**它们通过本身就是验收项之一**。

### 不是单元测试的验收（要显卡、要真实数据，人工跑一遍）

打开 `?scene=alocasia`，从 `sim.stats()` 和控制台读：

- `cfl < 1`，每帧步数 ≤ 24，`droppedTime == 0`。
- 锚定节点占**有质量节点**的比例落在一个合理区间（非零、且远小于一半）。为零说明判据没生效，
  接近全部说明半径取大了或者可动点没对上。
- `lattice.volume` 相对物体包围盒体积的占比。**超过三成就是封口把叶片桥接成一坨了**——这是
  "不透传 `fill`/`seal`"这个决定的回头条件。
- 手感：拖一片叶子，叶子动、花盆不动；射线点花盆抓不住；松手回弹；全程没有任何东西下落。

## Out of Scope

- **背景（scenery）不接**。590k 个背景高斯每帧都要重烘进 work buffer（`render/splats.js`），
  会把这个场景直接变成渲染压测，机制没跑通之前不该把渲染成本混进来。资产契约已经由"脚本输出
  最终世界坐标"定死，接的时候走 `scene.scenery` 这条已有的路，不需要重新设计。
- **另外三个场景**（carnations / hat / telephone）不接。它们是验收"只剩声明"这句话的手段，
  不是本轮交付物。
- **锚定结论怎么写进点阵**——三个候选（点阵级置零 / 新约束 / 应用层直接改 `Particles`）各有
  取舍，单独一张票：`issues/01-anchor-mechanism.md`。本 spec 里判据算出"谁该被锚定"，那张票
  决定"这个结论用什么机制生效"。
- **逐点物理属性**。官方有一个学出来的杨氏模量空间场（triplane，`sim_fields.pt`）。我们用
  均匀材料，不复刻。
- **官方的激励方式**。学出来的初速度场和冲量都不做——用仓库已有的抓取，这是"用我们自己的方式
  让它动"的全部内容。
- **填充/下采样的一比一还原**。官方按 `downsample_scale` 做 kmeans 下采样到一两万粒子；我们
  走体素点阵，不对齐粒子数。
- **`MAX_STEPS_PER_FRAME` 的提升**、**`fill`/`seal` 的透传**、**`DEFAULT_GRAB_RADIUS` 的调整**
  ——三个都是核心改动，都在没有证据之前不做。

## Further Notes

- **薄结构是这次最大的已知风险，而且它是 §4.2 收的费，不是缺陷**。体素点阵把 1 mm 的叶片印成
  一格（15.9 mm）厚的板。视觉上不受影响——高斯内嵌在点阵里，画出来仍然是薄叶；受影响的是
  **刚度**，弯曲刚度按厚度三次方走，所以要让它看起来会摆，E 必须比真实叶片组织低得多。这不是
  参数没调好，是代理几何的分辨率在说话。`?scene=alocasia` 打开点阵调试视图就能直接看见。
- **零重力把"锚定"从锦上添花变成必需**。重力为零的时候，唯一挡着被拖过的叶子飞出屏幕的是
  锚定集合和弹性约束。锚定集合一旦为空，这个场景就只是一团会被推走的高斯。
- 官方 demo 的泊松比是每次 `np.random.uniform(0.1, 0.4)` 随机抽的，不是训练出来的常数
  （`demo.py:630`，`requires_grad=False`，checkpoint 里也不存）。这看起来像官方的一个疏忽，
  记在这里以免有人以为那个数有出处。
- 声明高度 0.30 m 的核对：缩放 0.718，物体转正后 0.38 m 宽 × 0.30 m 高（叶展比株高宽，和照片
  一致），同一个变换推出的整间屋子是 2.20 × 3.17 m、层高 2.31 m。是间真房间。这个核对由脚本
  每次打印，不是一次性的手算。
- CLAUDE.md 新增的 Domain docs 段指向根目录 `CONTEXT.md` + `docs/adr/`，但项目文档规则那张表
  里没有它们，仓库里也还没有这两样东西。这次接入确实产出了几个新词（**前景物体** / **可动
  部分** / **锚定节点**），但要不要开 `CONTEXT.md` 是文档体系的选择，没有替使用者做主。
